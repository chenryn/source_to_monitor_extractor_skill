# 信号仲裁：先查已有什么，再谈缺什么

这份文档是为了防止一个高频且代价很高的错误：**只看了日志平面，就断言「这个项目缺少某项监控」。**

流程与业务领域无关。文中的词表和案例来自 `examples/` 下的输出示例，仅用于说明方法；**指标名、指标数量、端点路径一律不可跨项目复用**，实际检索用的关键词必须从本项目提取结果里的命名习惯推导（见 `../SKILL.md` Step 3）。

## 一、三平面职责矩阵

| 平面 | 数据形态 | 擅长回答 | 不擅长回答 | 采集方式 |
|---|---|---|---|---|
| **日志 (log)** | 离散事件文本 | 发生了什么、为什么失败、启动是否成功 | 分位数、趋势、跨实例聚合 | 采集 agent → Loki/ES |
| **指标 (metric)** | 时序数值 | 错误率、P99、水位、趋势、容量 | 单次请求的细节、失败原因 | 拉取端点 / push / OTLP / JMX / 外部 exporter（路径与协议按项目实测） |
| **链路 (trace)** | 请求级 span 树 | 这一次慢在哪一段、调用链断裂点 | 全局趋势（采样后不准） | OTLP → Tempo/Jaeger |

**判断口诀**：
- 要「率」「分位」「水位」「趋势」→ 指标
- 要「有没有发生」「什么原因」→ 日志
- 要「哪一段慢」→ 链路

## 二、仲裁流程（四步，缺一步都不能下结论）

### 第 1 步：把需求翻译成信号类型

| 用户/业务语言 | 信号类型 | 首选平面 |
|---|---|---|
| 「服务活着吗」 | 存在性事件 | 日志（启动成功）+ 指标（up） |
| 「用户觉得慢」 | 延迟分位 | 指标（Histogram） |
| 「成功率多少」 | 比率 | 指标（Counter 比值） |
| 「为什么这批请求失败」 | 错误上下文 | 日志 |
| 「扩容够不够」 | 资源水位 | 指标（Gauge）+ USE 方法 |
| 「这次请求卡在哪」 | 分段耗时 | 链路 |
| 「新版本有没有引入问题」 | 版本间对比 | 三平面 diff |

> 需求清单按 Step 0 的项目画像选取：在线服务以「率 / 分位 / 水位」为主，批处理还要有「作业完成 / 滞后 / 重试」，库/SDK 关注「暴露给宿主什么信号」。上表是常见映射，不是固定清单。

### 第 2 步：查该平面是否已有信号

```bash
# 查指标名（最高频的误判来源）
python - <<'PY'
import json
d = json.load(open('metrics_extracted.json'))
for r in d:
    if r['kind'] == 'definition':
        print(f"{r['name']:55s} {r['metric_type']:10s} {r['file']}:{r['line']}")
PY
```

**关键词不要照抄词表**：先从 `metrics_extracted.json` 里学出本项目的命名空间前缀、分隔符与命名模式，再按语义维度扩展同义词。通用起点：

| 语义维度 | 通用词根 | 领域扩展词（仅在画像确认后添加） |
|---|---|---|
| 延迟 / 耗时 | `latency` `duration` `elapsed` `seconds` `time` `cost` | 推理：`ttft` `itl` `e2e`；数据管道：`processing_time` |
| 错误 / 拒绝 | `error` `failure` `rejected` `timeout` `exception` `abort` | `preemption` `admission_rejection` `dead_letter` |
| 速率 / 吞吐 | `requests` `total` `count` `throughput` `qps` | `tokens` `messages` `rows` `bytes` |
| 排队 / 并发 | `queue` `waiting` `pending` `inflight` `backlog` `running` | `batch` `lag` |
| 缓存 / 状态 | `cache` `hit` `miss` `state` `status` | `prefix_cache` `checkpoint` |
| 资源水位 | `usage` `util` `memory` `pool` `connections` `bytes` | `gpu` `kv_cache` `fd` |

检索时同时试「源码构造名」与「暴露名」：SDK 常补后缀（`_total`）、改分隔符、注入命名空间前缀。

### 第 3 步：没有时，判断是「真缺口」还是「提取遗漏」

这是最容易出错的一步。三种情况要分开：

| 情况 | 判定依据 | 结论写法 |
|---|---|---|
| **真缺口** | 指标列表里没有，且全仓库搜关键词也无定义 | 「需新增埋点」+ 指定插入位置 |
| **提取遗漏：自定义 DSL** | 有 `ns:name` 形式的字符串字面量，但没匹配到构造器 | 「源码中存在，需人工确认定义位置」 |
| **提取遗漏：动态命名** | `name=f"{prefix}:{x}"`、`name=NAME`（参数传入） | 「指标名运行时拼接，查调用点确认」 |
| **提取遗漏：脚本不支持** | 项目语言/SDK 不在 `SKILL.md` Step 0 的能力矩阵内 | 「人工提取，覆盖率未知」+ 列出未覆盖范围 |

`extract_metrics.py` 的汇总会给出「已解析定义 / 未匹配到构造器」的区分，例如：

```
指标名覆盖率                     : {已解析}/{字面量引用总数}
仅有名字引用、未匹配到构造器     : N 个（自定义指标 DSL 或跨模块定义，需人工确认）
    - <项目命名空间>:<某指标名>
```

**看到「未匹配到构造器」的列表，不能说这些指标不存在**——它们可能真实存在，只是定义方式不是脚本认识的标准构造器。

### 第 4 步：写进仲裁表

每条监控需求一行，必须填满：

| 需求 | 平面 | 现有信号 | 源码位置 | 结论 |
|---|---|---|---|---|

## 三、案例：三平面互补（完整记录见 `../examples/vllm-monitoring-plan.md`）

某在线服务第一版只扫了日志，得出「缺少请求级延迟监控，建议新增埋点」。**前半段事实正确，结论错误**：

1. 请求级延迟分位本就不该由日志承担——日志做分位数既不准又贵。
2. 该项目在指标平面已有完整的延迟分布、排队时间、资源水位与拒绝计数，只是分析时没查这一平面。
3. 真正的缺口在源码之外：平台/硬件层指标需要外部 exporter，属于「需外部组件」而非「需新增埋点」。

**与项目无关的教训**：

- 「某个平面没有」≠「没有监控」。平面之间是互补的，不是替代的。
- 日志做事件，指标做度量。**用日志去做指标该做的事，是最常见的架构错误。**
- 完整指标名、仲裁表与结论见对应样例文件；**该样例的指标名不适用于其他项目**。

## 四、常见误判清单

| 误判 | 事实 |
|---|---|
| 日志里没有延迟打印 → 没有延迟监控 | 延迟分位通常在 Histogram / Summary 里 |
| 搜不到标准构造器 → 没有指标 | 可能有自定义 DSL、工厂函数、注册表、常量拼接、动态命名 |
| 没有同名端点 → 没有指标 | 可能走 push / OTLP / JMX / 独立端口 / 外部 exporter，或端点路径与协议完全不同 |
| 提取脚本输出为 0 → 没有该平面 | 先看语言与 SDK 是否在能力矩阵内；未覆盖时必须走人工提取降级路径 |
| 有 trace 代码 → 生产开了 trace | 通常默认关闭，要显式配 endpoint 和采样率 |
| 有指标定义 → 指标有数据 | 可能被 `if` 条件包住、默认配置下不注册，或无写入点 |
| 指标有定义 → 告警就该用它 | 先确认该指标在本项目的语义、量纲与单位 |
| 只扫主语言 → 结论可信 | 多语言仓库里，另一语言可能承载了整个关键层 |

## 五、写结论时的句式要求

**错误句式**：
> 「缺少 X 监控」「没有 Y 指标」

**正确句式**：
> 「日志平面无 X 相关埋点（已检索 N 条）；指标平面无 X 定义（已检索 M 个指标名）；链路平面无 X 相关 span。结论：X 属于真缺口，建议在 `<文件>:<函数>` 新增 `<具体做法>`。」

三平面都查过，才有资格说「缺」。
